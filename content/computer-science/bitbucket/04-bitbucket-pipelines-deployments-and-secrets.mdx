# Bitbucket Pipelines, Deployments, And Secrets

Bitbucket Pipelines turns repository events into automated build, test, security, and deployment workflows.

## What are we learning?

We are learning how Bitbucket Pipelines works from first principles: YAML configuration, steps, caches, artifacts, variables, secrets, environments, and Deployments.

## Why does it matter?

CI/CD is the bridge between reviewed code and running systems. A bad pipeline is slow, flaky, insecure, and easy to bypass. A good pipeline gives fast feedback, protects secrets, records deployments, and supports recovery.

## What problem does it solve?

Pipelines answer: "Can this change build, test, scan, package, and deploy in a repeatable way?"

Deployments answer: "Which code went to which environment, when, and through what workflow?"

Variables and secrets answer: "How does automation access configuration without hardcoding credentials in Git?"

## Prerequisites

Know pull requests, branch protections, CI/CD basics, and why secrets must not be committed.

## Core concepts

| Concept | Meaning |
| --- | --- |
| `bitbucket-pipelines.yml` | Repository CI/CD definition |
| Step | A unit of execution, usually inside a container image |
| Pipeline trigger | Branch, pull request, tag, custom, or schedule event |
| Cache | Reused dependency data to speed builds |
| Artifact | File passed or preserved after a step |
| Variables and secrets | Configuration values scoped to workspace, repository, deployment, or pipeline |
| Deployment | Environment-targeted release record |

## Internal workings

Typical flow:

```text
push or PR update
  -> Bitbucket selects matching pipeline
  -> runner executes steps
  -> status attaches to commit/PR
  -> artifacts and reports are stored
  -> deployment step records environment release
```

Merge checks can require pipeline success before merge.

## Design decisions

Design pipelines in lanes:

| Lane | Goal | Example |
| --- | --- | --- |
| Pull request | fast correctness feedback | lint, unit tests, type checks |
| Main branch | integration confidence | full tests, package, image build |
| Release tag | reproducible release | publish artifact, create deployment |
| Manual custom | controlled operations | database migration, rollback |

Keep PR pipelines fast. Put slow exhaustive checks where they add real value.

## Alternatives

Bitbucket Pipelines is integrated and convenient. External CI systems may be better when teams need specialized runners, complex orchestration, or cross-repository build graphs. The tradeoff is integration simplicity versus CI platform depth.

## Common misconceptions

- "Secrets are safe if the repository is private." Secrets should still live in protected variable stores.
- "A green pipeline means deploy is safe." It means configured checks passed. Release safety also needs observability and rollback.
- "Caches are always good." Bad cache keys can hide dependency changes or create flaky builds.
- "Every pipeline should deploy." Separate verification from deployment unless continuous deployment is intentional.
