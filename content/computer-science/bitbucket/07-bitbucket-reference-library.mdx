# Bitbucket Reference Library

This is the source map for building and maintaining the Bitbucket track.

## What are we learning?

We are learning where to look for authoritative Bitbucket behavior and how to classify sources by topic.

## Why does it matter?

Bitbucket has product-specific behavior. Pull request rules, Pipelines syntax, deployment environments, branch restrictions, and Jira integration should be grounded in Atlassian documentation, not memory.

## What problem does it solve?

This page solves the maintenance problem. Future authors can expand Bitbucket content from a known source base instead of re-researching every page.

## Prerequisites

Know the Bitbucket platform model and the Git concepts behind branches and pull requests.

## Internal workings

Use source classes:

```text
Bitbucket platform behavior -> Atlassian support docs
API behavior -> Atlassian developer docs
Git behavior -> git-scm official docs
workflow recommendation -> Atlassian docs plus engineering practice sources
team policy -> clearly labeled recommendation
```

## Design decisions

Every Bitbucket page should include:

1. Platform concept.
2. Git concept underneath it.
3. Team workflow consequence.
4. Failure mode.
5. Atlassian reference link.

## Alternatives

Blogs and community answers are useful for edge cases, but they should not be the canonical source for platform behavior. When a blog conflicts with Atlassian docs, prefer the docs and describe the blog as a case study.

## Common misconceptions

- "Bitbucket docs are only UI instructions." They also define platform constraints and workflow behavior.
- "Git docs are enough for Bitbucket." Git docs explain repository mechanics, not Bitbucket merge checks, Pipelines, or Jira integration.
- "Reference libraries are optional." They make future content reviewable and maintainable.
