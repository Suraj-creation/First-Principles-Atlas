# Git And GitHub Reference Library

This is the source map for the Git and GitHub learning system. The Atlas should synthesize these materials into original, first-principles explanations so a learner can get the core mental model here, then use the sources for exact syntax, edge cases, and deeper research.

## What are we learning?

We are learning which references should inform each part of the Git and GitHub curriculum: beginner mental models, workflows, internals, collaboration, security, automation, governance, and future AI-native improvements.

## Why does it matter?

Without a reference map, content becomes opinion. With a reference map, the Atlas can remain concise while still being grounded in authoritative material.

The goal is not to copy books. The goal is to cover the concepts those books teach in original language, with links back to the sources that establish command behavior, platform behavior, and engineering practice.

## What problem does it solve?

It solves three problems:

1. Coverage: we can see which sources back each topic.
2. Trust: readers know where claims come from.
3. Maintenance: future edits can update source-backed pages without searching from scratch.

## Common beginner confusion

| Confusion | Better source habit |
| --- | --- |
| "A blog said this workflow is best." | Treat blogs as situated advice. Check official docs and team context. |
| "The book says Git stores snapshots, so diffs do not matter." | Git stores snapshot objects, but diffs are essential computed views for review. |
| "GitHub Docs explain Git." | GitHub Docs explain the platform. Use Git docs for Git command and object behavior. |
| "Stack Overflow answer means policy." | Answers solve local symptoms. Team workflow needs explicit policy and recovery paths. |

## Internal workings

Reference quality should be recorded per page:

```text
claim type:
  command behavior -> official Git docs
  platform behavior -> GitHub Docs
  workflow recommendation -> official docs plus engineering practice source
  advanced internals -> Git technical docs
  future idea -> clearly labeled research or proposal
```

This prevents workflow opinions from being presented as universal truth.

## Design decisions

The Atlas should use source classes:

| Class | Trust level | Use |
| --- | --- | --- |
| Official command/platform docs | Highest for behavior | Syntax, defaults, constraints |
| Official books | High for conceptual learning | Mental models and examples |
| Engineering practice guides | High but contextual | Team workflows and review norms |
| Blogs | Medium | Case studies and tradeoffs |
| Forum answers | Low unless verified | Symptoms, edge cases, debugging clues |
| Experiments | Clearly labeled | Future and research sections |

## Alternatives

An alternative is to put references only at the bottom of each page. That is still necessary, but not sufficient. A central library lets future authors see coverage gaps and avoid re-researching the same source set.

## Common misconceptions

- "Comprehensive means long." Comprehensive means all important concepts are covered at the right depth. Some sections should be short.
- "References are decorations." References are the maintenance backbone of the Atlas.
- "Books can be replaced by summaries." The Atlas can replace first-pass learning for many readers, but canonical books and docs remain sources for exactness and further study.

## Advanced section: coverage contract for replacing first-pass book reading

To make the Atlas strong enough that readers do not need to start by reading whole books, each major Git/GitHub area should have:

1. A first-principles explanation.
2. A confusion map.
3. A visual or state model.
4. A practical workflow.
5. A failure and recovery section.
6. A professional/team-use section.
7. A source-backed reference list.
8. A short memory summary.

This does not copy books. It absorbs their conceptual value into an editable, source-linked knowledge system.
